**Dashboard Firebase audit — September 12, 2026**

The security migration left many dashboard controls connected to direct client writes that production now denies. Other controls reach a deployed callable but disagree with its allowed roles or job states. This is a confirmed integration problem, rather than a general Firebase outage.

This audit identifies 20 affected workflow groups. A group can contain several buttons. It does not claim that every button in that group fails for every account, or that 218 tests represent 218 separate bugs.

**Evidence and scope**

- Read the live Hosting release, deployed Firestore/Storage/Realtime Database rules, and metadata for 171 deployed functions. No production application records were changed.
- Hosting: `wellbuilt-sync`, version `f1ce14ad51e92242`, released September 11 at 05:29:25 UTC (September 11, 12:29 a.m. Chicago).
- Downloaded the Hosting file manifest and all 70 listed JavaScript files. The 69 application JavaScript assets match the manifest's SHA-256 hashes when compressed with Firebase CLI's gzip level 9. `/__/firebase/init.js` is Firebase's generated endpoint and is excluded from the application hash claim.
- Downloaded the deployed source archives for `dismissDispatch` and `adminEmployeeDashboardAccess`. Ran the deployed dismissal decision code with nine synthetic job states and the deployed authority helper with six synthetic roles.
- Replayed the actual production Firestore and RTDB rules in isolated local emulators: **218/218 permission expectations matched**. These tests deliberately prove that the legacy writes are denied, and include allowed reads as controls. They are not successful end-to-end business transactions.
- Indexed the candidate September 10 release source: 305 Firebase SDK call sites (140 mutation calls, 115 reads/listeners, 50 callable constructors). Those are source inventory counts, not exact live-button counts. Live bundle evidence controls conclusions when source differs.
- Examined Dispatch, Admin/Employees/Companies/Wells/GPS, Settings, Billing, Payroll, Chat, Well, Mobile, Equipment, Tickets, Driver Logs, and shared data helpers. No authenticated human session was used to click production mutation buttons. Device-specific layout and real-account exceptions remain outside this verification.

**The reported Active Jobs card**

The user's wording was “I can dismiss a job card on level 1”; clarification about whether this meant “can't” is still pending. This audit does not assume a particular live job was dismissed or that its state should permit dismissal.

In the inspected UI, the collapsed driver-card header toggles expansion. Individual expanded job rows expose X, while declined/cancelled cards have a separate Dismiss button. The confirmed defect is that an active row's X calls a terminal-state dismissal operation. For a properly scoped record and permitted caller, the deployed decision matrix is:

| Job state | Deployed dismiss result |
| --- | --- |
| Pending / pending approval | Reject: `not_dismissable` |
| Accepted / in progress / paused | Reject: `job_in_progress` |
| Declined / cancelled | Allow |
| Completed | Reject: `not_dismissable` |
| Already dismissed | Idempotent success |

Split jobs additionally enforce family company scope and reject dismissal if a sibling is started. Those protections should remain in place. The required product decision is whether each control means cancel the operational job, acknowledge a declined/cancelled job, or hide an already-finished item.

**Additional access and release risks**

The deployed `adminEmployeeDashboardAccess` source updates RTDB `users` and driver linkage, but does not itself create/update a Firestore `staff` record or staff custom claims. The production rules depend on those separate authorities. The emulator confirms that an RTDB-only admin profile can read its own profile but cannot read the company through Firestore. Whether a separate provisioning process fills the gap for each real account remains to be verified; no real-user access outage is inferred solely from this source observation.

The working checkout's `firebase.json` points at an RTDB rule file with root `.read:true` and `.write:true`. The live RTDB root denies both, and its writes remain locked down. Local Firestore rules are also materially older and more permissive. A blanket deployment from that checkout could undo security protections. Reconcile the release/configuration baseline before deployments, and deploy only the reviewed targets. This is a concrete observed deployment risk, not a reason to loosen production rules to make buttons work.

There is no single verified Git commit covering today's Hosting assets and all independently deployed functions. The current local checkpoint, candidate release branches, and production differ. The diesel repair and company-onboarding call sites demonstrate why a commit alone cannot establish that a button is fixed in production.

Existing source tests named “write inventory” actually assert that some denied legacy writes are still present. They document migration debt; they do not verify those buttons work. Build success and those tests therefore miss this class of regression. Replace those inventory assertions progressively with positive UI-to-authorized-operation tests and negative unauthorized-operation tests.

**Paths already using server operations**

Dispatch mutations, Add Well, pull deletion, secure driver administration, company contract administration, and canonical eQuipment operations have server routes and corresponding deployed functions. That avoids the specific direct-write failure, but is not an end-to-end certification: Dispatch already demonstrates a callable can still use the wrong role/state policy.

Photo-requirement metadata is an explicit exception in production Firestore rules: a platform admin can save it. The emulator positive control passed. The live sample-image uploader explicitly selects `wellbuilt-sync.firebasestorage.app`, where production Storage rules allow platform-admin image uploads under `photo_requirements`. Do not classify all photo controls as broken just because other paths are locked down. Storage uploads were inspected, not exercised in these emulator tests.

**Repair order and acceptance**

1. Establish the live release baseline and preserve the deployed rule denials. Fix Dispatch's action/state contract and operation-specific role authorization first, using synthetic pending, active, declined, cancelled and split jobs.
2. Repair employee role/deactivation/revocation controls and reconcile RTDB/Firestore/Auth provisioning. Verify a revoked account loses the intended access and an unrelated company's records remain inaccessible.
3. Migrate the shared company-settings writer and legacy company onboarding/administration routes. This clears many Settings buttons at once while retaining protected contract fields.
4. Repair manual pull creation/correction, billing/payroll ledger mutations, and tenant-scoped reads. Require server receipts, idempotent retries, transactional numbering, and field-result verification.
5. Finish project/chat operations, route administration, JSA templates, SWD, R&D, and legacy equipment specs. Verify compound operations do not leave partial records.

For each repair: test allowed and denied roles, same-company and cross-company access, actual before/after state in local fixtures, duplicate submission/retry, and visible failure feedback. Commit a coherent change, deploy the specific frontend/backend targets, then verify that Hosting's live bundle and the function revision contain the fix. Keep an explicit status of found / fixed in Git / deployed / verified live.
